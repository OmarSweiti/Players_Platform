## Identity and session boundary

The application owns authorization, membership and application sessions; the external OIDC provider owns credentials, verification and factor recovery. Keycloak is the development/staging default, with an exact release and image digest pinned in `0.5.1`. `start-dev` is permitted only in isolated development. Staging uses production configuration, TLS and a restricted administrative plane. Production identity hosting/provider remains [OPEN](../implementation/00-master-plan.md#open-register); evaluate data flows, region, MFA assurance, recovery, logout events, operational responsibility and restore capability before live use. A provider's certification does not certify this application.

Nest is the confidential OIDC client: authorization code, PKCE, state and nonce; validate issuer, audience, signature/algorithm, expiry, nonce and approved metadata/JWKS endpoints. Pin issuer configuration, restrict outbound endpoints, bound JWKS fetches and handle signing-key rotation without accepting arbitrary keys. Consume each login attempt once; validate exact callback and allowlisted return paths. Bind state to the initiating browser, not just a database row: the attempt records the existing session for a step-up, or a short-lived `__Host-sodara_preauth` cookie for a logged-out browser. The callback requires the matching binding and state before exchanging the code, then sets a new authenticated session. The pre-auth cookie is never accepted on business routes. Step-up binds and preserves the current session until successful replacement. Use the configured GET/query callback with SameSite=Lax; an arbitrary valid callback URL from another browser must fail. This browser binding follows the user-agent-session protection described by [OAuth Security BCP, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html). Short-lived protocol state expires and is removed. No password form, password reset, local TOTP, locally minted access token or alternate legacy route remains usable after `0.1.6`/`0.1.7`.

Global Identity is unique by `(issuer,subject)`. Tenant User is a membership unique by `(tenantId,identityId)`. Email is contact/invitation matching data, never account-link proof. Existing IDs and domain FKs survive migration; unlinked legacy memberships remain disabled. The host selects a candidate tenant through an exact configured registry match. A fixed AuthBootstrapRepository may look up only the session and membership under that host scope; it creates an authorized TenantContext only after the session, tenant and membership are valid. Client tenant IDs, forwarded host headers from untrusted proxies and provider role claims cannot grant membership.

Web and API share one origin through path routing: `/` goes to Next; `/api/` goes to Nest. Development uses the same path routing through a local HTTPS proxy (`0.2.1`). The browser receives one opaque `__Host-sodara_session` cookie with HttpOnly, Secure, SameSite=Lax and Path=/, and no Domain attribute. Generate at least 32 random bytes; persist only its digest in UserSession. Store derived issuer/subject/provider sid/acr/amr/auth_time; **do not persist provider access, refresh or ID tokens**. Next renders navigation and invokes the generated API contract; the API remains the authorization boundary. Configure development HTTPS so the cookie contract is tested rather than weakened.

Every protected request reads PostgreSQL session and current membership state. Check revokedAt, idle/absolute expiry, active tenant/member, selected tenant/user/identity consistency, required assurance and applicable policy before domain access. Session renewal updates idle expiry without extending absolute expiry; avoid a per-request write when the last-seen update can be bounded without weakening expiry enforcement. A cache is a later optimization only with a tested revocation-consistency protocol. Provisional expiry is 30 minutes idle and 12 hours absolute; owner approval is OPEN. Sensitive session responses use `Cache-Control: no-store`.

Rotate the opaque handle on authentication, step-up and authorized active-membership selection. Cross-host tenant changes require an authorized session establishment on the target canonical host; do not widen cookie Domain. Clear tenant/projection-sensitive browser query caches on logout/switch. Logout revokes the database session before clearing the cookie; session-management endpoints list real sessions and may revoke only the caller's permitted scope. App deactivation/role changes take effect on authorization checks after their transaction commits and revoke sessions where policy requires. Already-running sensitive commands recheck relevant policy/version preconditions before committing; revocation does not retroactively cancel a completed operation. Realtime operations inherit these checks; long connections cannot keep revoked access indefinitely.

Back-channel logout validates the provider signature, issuer, audience, event claim, time/replay constraints and sid/subject linkage before revocation. Enumerate TenantRegistry entries with potentially live matching sessions, including disabled tenants, and revoke within tenant transactions so later reactivation cannot revive provider-logged-out access; do not invent a global bypass session client. A validated subject-only event revokes all matching issuer/subject sessions; missing both sid and subject is rejected and must not become an unfiltered query. Provider-side disable, password/factor changes and revocation become effective when a validated event arrives or the app session expires. **This exposure window is OPEN for owner acceptance**; immediate app revocation does not imply immediate provider-event delivery. Required provider audit events, including MFA/recovery/lockout, need authenticated ingestion or a documented accessible provider audit source; do not infer them from successful login alone.

Privileged access requires tested provider-specific `acr`/`amr` assurance and sufficiently recent `auth_time`. Missing assurance triggers step-up or denial, never a role-only bypass. Sensitive actions—role/support grants, credential-management redirects, evidence approval/signing and future payouts—require recent authentication. The exact freshness/role policy is OPEN; use a conservative five-minute step-up window for these actions until approved. Provider factor reset/recovery must not silently restore privileged assurance.

For unsafe browser methods require an exact Origin match, synchronizer CSRF token bound to the session and approved content type. `0.5.6` derives the synchronizer token as an HMAC of the session-token digest under a keyed, rotatable secret — nothing is stored — and `GET /api/v1/auth/session` returns the same token to every tab until the session rotates, with no-store. Use constant-time token comparisons and safe-method semantics. CORS is closed by default; it is not the CSRF control. Explicit protocol exceptions cover only validated OIDC callbacks, authenticated provider webhooks and back-channel logout; do not exempt the entire auth path. Apply CSP, output encoding, safe redirects and dependency controls: HttpOnly limits token reading but does not make XSS harmless.

## Authorization, field classification and role defaults

The permission catalog is explicit code (`0.6.1`), not dot-splitting into enums. Route coverage fails for any protected operation without a declared permission (`0.6.2`). Use cases evaluate membership, action, object relationship, classification, lifecycle/approval eligibility, support scope and authentication assurance (`0.6.3`). A permission decorator alone does not authorize an object or its fields. Reject forbidden write properties; do not silently accept tenantId, role, confidential flags, workflow status or money fields because they exist in a Prisma model.

The following classifications merge the data taxonomy with a safer default. **OPEN — the agency must approve field-level classifications and recipient rules.** Until then sensitive fields are denied unless an explicit reviewed permission and object/purpose policy permits them. A field marked sporting/internal is not automatically public.

## Tenancy and runtime boundaries

Four independent controls apply: verified context → explicit scoped repositories and use-case policy → composite/same-parent FKs plus ENABLE/FORCE RLS → adversarial two-tenant tests. `withTenantTransaction(ctx,fn)` sets transaction-local `app.tenant_id` and every query uses that transaction client. `sodara_owner` is NOLOGIN, `sodara_migrator` is deployment-only, and `sodara_app` is non-owner NOBYPASSRLS with no privileged role membership. New tenant tables ship policies/grants/tests in their creating migration. Tenant-bearing outbox/inbox rows are included.

TenantRegistry exposes only routing/discovery metadata; workers enumerate IDs then claim/process under one tenant transaction at a time. Jobs carry stable references and tenant context, not copied user JWTs or clinical text. Re-evaluate current recipient/source authorization when releasing exports, notifications and signed URLs. Caches include tenant, subject/projection and permission version as appropriate. Websocket rooms include tenant/conversation; handshake, join, every send/read and reconnect are checked against current session and membership. Redis/Valkey namespaces alone are not authorization.

A runtime credential compromise can set arbitrary tenant context; RLS prevents accidental omitted predicates, not every hostile application process. Storage, backups, operator roles and identity configuration remain separate trust boundaries requiring least privilege and recovery tests. No RLS, encryption or opaque ID claim replaces same-tenant field/object policy.

## Confidential-data lifecycle, files and evidence

Before live data, inventory each sensitive field/object's purpose, owner, recipients, source, region, encryption/key handling, retention/hold rule and restoration implications. Medical authority, guardian consent, privacy notices, cross-border data flows and applicable legal obligations require agency/counsel decisions. No jurisdiction or deadline is inferred from Arabic support, JOD or Asia/Amman. Synthetic data is the default outside production. Medical/scouting remain server-quarantined until their release gates; no session replay or third-party analytics captures restricted pages.

TLS and approved encryption at rest are baseline. High-risk narrative/identity field encryption and searchability need a reviewed design covering key IDs, least-privilege decrypt paths, rotation, backups and recovery before live acceptance. Encryption does not make an unauthorized projection safe. Do not adopt deterministic encryption or searchable indexes for confidential text without a separate leakage analysis. Raw secrets, tokens and bodies are excluded from logs, errors, traces and audit payloads; record structural changes and protected references instead.

Files use FileObject/UploadSession, private quarantine, size/type/magic-byte checks, ClamAV, immutable final promotion with SHA-256 plus provider versionId, and authorized downloads bound to the version. The original presigned PUT must be unable to replace released bytes. Keep the scanner/transform process resource-constrained, updated and without broad database/provider credentials; parser failure never becomes CLEAN. Propagate source classification to variants and exports. Signed URL TTL bounds the post-issuance revocation window; the owner must accept that window, and highly sensitive downloads may require an authenticated streaming path. Revocation prevents new URLs but cannot revoke already downloaded bytes.

ContractVersion, ApprovalDecision and SignatureEvent receive the same UPDATE/DELETE/TRUNCATE protection as audit. Evidence collection in Phase1 does not itself authorize SIGNED. An approved evidence policy must define signatory authority, exact version/hash, method, verification, approval completeness, retention and exception handling. Counsel/provider questions remain OPEN. An approved manual method may satisfy SR-CT-008; provider integration SR-CT-011 is delivered in Phase3 under the [documented deferral](../implementation/00-master-plan.md#deferred-requirements). A completion webhook or uploaded PDF alone cannot bypass the policy.

Archive operational records; purge only through an approved retention mechanism respecting holds and all copies: original object versions, variants, exports, caches/search indexes, provider artifacts and backups. Keep evidence identities without unnecessary sensitive content. A backup may retain archived data until its approved expiry; restore must reapply suppression/tombstones and revoked access. No automatic purge is enabled while retention is OPEN. Local recovery is rehearsed on disposable services in `0.10.3`; `1.10.5` prepares staging recovery and `1.10.13` independently rehearses PostgreSQL, objects, identity configuration and key recovery with measured RPO/RTO.

## Secrets, keys and incident handling

Development secrets are uncommitted local configuration; production uses the approved host secret store. Boot refuses missing/placeholder values. Inventory OIDC client credentials, storage/queue/mail credentials, database role secrets and encryption key IDs with owner, purpose, allowed consumers and rotation runbook. Do not create an application JWT signing-key lifecycle for the retired auth system. Provider signing keys are validated public keys, not stored login tokens. Rehearse credential/key rotation and recovery in staging (`1.10.3`/`1.10.5`/`1.10.13`). Invitation tokens are generated by the delivery handler at send time (`0.7.8`, with `0.5.10`) and stored only as hashes; outbox payloads carry the invitation id, never a link, and the raw link is never logged. A resend issues a new token and invalidates the old one. If a secret is found in a tree, contain/revoke it first; history rewriting requires separate owner authorization.

Suspected cross-tenant or confidential exposure triggers immediate incident containment: disable the affected route/job/share, revoke affected app sessions/grants, preserve restricted evidence, identify scope and notify the designated incident owner through approved channels. Do not purge or modify audit to tidy the incident. The agency/counsel decides required external notifications and timing under the approved incident policy; this document invents no legal deadline. The launch runbook (`1.10.9`) records contacts, severity, containment, restoration criteria and post-incident actions. Tools must not automatically message outside parties without authorization.

Before each slice, write the actor/action/tenant/object/fields, trust-boundary change and one abuse case.
